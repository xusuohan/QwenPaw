## 1. 背景与目标

### 1.1 现状

QwenPaw 便携版基于 **conda-pack** 构建，pipeline 为：

```
wheel build → conda create → pip install → conda-pack → unpack → compileall → 平台打包
```

当前存在三大问题：

1. **构建耗时过长**：未精确测量，预估 10-20 分钟（含网络下载）
2. **包体体积臃肿**：产出 500MB-1GB，未系统分析各依赖占比
3. **多架构适配缺失**：仅构建 macOS arm64 / Linux x86_64 / Windows x86_64；用户本机 Intel Mac 无法本地构建；Windows 便携版偶发运行失败

### 1.2 目标

| 维度 | 当前 | 目标 |
|---|---|---|
| 构建耗时（缓存命中） | 预估 10-20 分钟 | < 5 分钟 |
| 构建耗时（缓存未命中） | 预估 15-30 分钟 | < 10 分钟 |
| 包体体积 | 500MB-1GB | profiling 后确定合理目标 |
| macOS 架构支持 | 仅 arm64 | arm64 + x86_64 |
| Windows 可靠性 | 偶发运行失败 | smoke test gate，失败即诊断 |

### 1.3 方案选择

**方案 A：增量优化当前 conda-pack 流水线**（已确认）

保留 conda-pack 架构，通过 profiling 数据驱动逐阶段优化。不迁移打包工具。

理由：
- 当前流水线已有 env 缓存、hash-based .pyc 等成熟机制
- profiling 可能揭示的优化空间比预想更大
- 多架构问题本质是 CI 配置问题，不需要改变打包方案
- Windows 运行失败是诊断问题，不应驱动打包方案迁移

## 2. 硬约束（继承自便携版设计）

| # | 约束 | 含义 |
|---|---|---|
| C1 | **USB 便携版优先（exFAT）** | 构建产出需兼容 exFAT：无 UNIX 权限、无 journaling、随机 IO 延迟高 |
| C2 | **单实例，仅进程内并发** | 构建脚本不需要跨进程协调 |
| C3 | **可接受小幅行为变更** | 裁剪依赖、调整压缩级别等均可用 |
| C4 | **不碰宿主磁盘** | 所有裁剪在构建期完成，不影响运行时 |
| C5 | **分阶段推进** | 先本机 Intel Mac profiling + 优化，再扩展其他架构 |

## 3. 设计详情

### 3.1 Phase 1：Profiling 基础设施

#### 3.1.1 构建耗时 Profiling

**改动文件**：`scripts/pack/build_common.py`

在 `main()` 的每个关键阶段包裹计时：

```
阶段分解（build_common.py 内）：
1. conda_create     — conda create -n ... python=3.10 pip
2. pip_install      — pip install qwenpaw @ <wheel>
3. pip_uninstall    — pip uninstall kubernetes sympy
4. pip_cache_purge  — pip cache purge
5. conda_fix        — conda install pip setuptools wheel conda-pack
6. conda_pack       — conda-pack -n ... -o ... --compress-level 4
```

**改动文件**：`scripts/pack/build_macos.sh`、`build_linux.sh`、`build_win_portable.ps1`

```
阶段分解（平台脚本内）：
7. unpack           — 解压 conda-pack 归档
8. compileall       — python -m compileall --invalidation-mode checked-hash
9. platform_pack    — 平台特定打包（.app bundle / tar.gz / zip）
```

**输出格式**：`dist/build_profiling.json`

```json
{

  "python_version": "3.10.14",
  "wheel_hash": "abc123...",

      "name": "conda_create",
      "start_ts": 1719235200.0,
      "end_ts": 1719235260.0,
      "duration_s": 60.0,
      "exit_code": 0
    }
  ],

```

#### 3.1.2 包体体积 Profiling

**新增文件**：`scripts/pack/analyze_packages.py`

功能：
1. 解压 conda-pack 归档到临时目录
2. 用 `du -sh` 按顶层目录统计各包大小
3. 用 `pip show` 交叉比对直接依赖 vs 传递依赖
4. 识别大文件类型分布（`.so`/`.dylib`/`.pyd`、`.py`、`.pyc`、数据文件）
5. 输出 `dist/package_size_report.json`

输出格式：

```json
{
  "total_size_mb": 650,
  "packages": [
    {
      "name": "numpy",
      "version": "1.24.3",
      "size_mb": 45.2,
      "type": "direct_dependency",
      "top_files": ["numpy/core/_multiarray_umath.cpython-310-darwin.so"]
    }
  ],
  "file_types": {
    ".so": {"count": 120, "total_mb": 200},
    ".py": {"count": 5000, "total_mb": 80},
    ".pyc": {"count": 5000, "total_mb": 60}
  }
}
```

#### 3.1.3 Windows 诊断

**改动文件**：`scripts/pack/build_win_portable.ps1`

在构建完成后增加：
1. Smoke test：`& "$env_dir\python.exe" -c "import qwenpaw; print(qwenpaw.__version__)"`
2. 收集 `conda-unpack` 完整输出到 `dist/unpack_log.txt`
3. Smoke test 失败时收集诊断信息（Python 版本、PATH、已安装包列表）

**改动文件**：`.github/workflows/build-portable.yml`

Windows job 增加 smoke test 步骤，失败则上传诊断日志作为 artifact。

### 3.2 Phase 2：基于 Profiling 数据的优化

**前置条件**：Phase 1 profiling 数据已产出。

#### 3.2.1 构建耗时优化

按 profiling 中各阶段耗时占比，从高到低逐个处理。已知潜在优化点：

| 阶段 | 潜在优化 | 预期收益 |
|---|---|---|
| `pip install` | 预下载 wheel 到 `.cache/pip_wheels/`，用 `--find-links` 离线安装 | 消除网络波动，减少 30-60s |
| `conda-pack` | 对比 `--compress-level 1` vs `4` vs `9` 的耗时/体积比 | 可能节省 30-50% 压缩时间 |
| `compileall` | 考虑在 conda-pack 前预编译（避免解压后再编译的 IO） | 减少平台脚本中的 compileall 耗时 |
| `conda create` | 未命中缓存时用 `--clone` 从基线环境复制 | 比 resolve + install 快 |

**原则**：不做无数据支撑的优化。每个优化项都需要 profiling 前后对比验证。

#### 3.2.2 包体体积优化

按 `package_size_report.json` 中各包大小占比，从大到小逐个处理。优化手段按侵入性从低到高：

| 手段 | 预期收益 | 风险 | 验证方式 |
|---|---|---|---|
| 删除 `tests/`、`docs/`、`examples/`、`*.rst` | 10-30MB | 低 | import 验证 |
| Strip debug symbols（`strip -x *.so *.dylib`） | 20-50MB | 低 | import 验证 |
| 删除 `.a` 静态库文件 | 10-30MB | 低 | import 验证 |
| 识别并移除传递依赖中的大包 | 取决于 profiling | 中 | 全量 import 测试 |
| 删除重复文件（pip+conda 双份安装） | 取决于 profiling | 中 | 全量 import 测试 |

**安全验证流程**：
1. 应用裁剪操作
2. 运行 `python -c "import qwenpaw; print('OK')"` 确认无 import 错误
3. 运行 `pytest tests/unit/ -q --timeout=60` 确认功能正确
4. 如果验证失败，回滚该裁剪操作并记录到排除清单

### 3.3 Phase 3：多架构适配

#### 3.3.1 macOS Intel (x86_64) 支持

**CI 改动**：`.github/workflows/build-portable.yml`

```yaml
jobs:
  build-macos-arm64:
    runs-on: macos-latest  # Apple Silicon（已有）
    # ...

  build-macos-x86_64:
    runs-on: macos-13      # Intel（新增）
    # ...
```

两个 job 结构相同，仅 runner 不同。产出目录加架构后缀：
- `QwenPaw-Portable_macOS-arm64_<timestamp>/`
- `QwenPaw-Portable_macOS-x86_64_<timestamp>/`

**本机构建**：在 Intel Mac 上直接运行 `make portable`，conda 自动安装 x86_64 包。无需交叉编译。

**不需要 universal binary**：conda 环境天然是架构特定的，做 universal 需要 lipo 合并两个环境，成本极高且收益仅是"一个包跑两架构"。

#### 3.3.2 Windows 运行失败诊断

见 §3.1.3（smoke test + 诊断日志收集）。

如果 smoke test 在 CI 中复现失败，根据诊断信息定位根因（预期可能是 conda-unpack bug #154 的变体，或长路径问题的新触发场景）。

#### 3.3.3 构建矩阵总结

| 平台 | 架构 | CI runner | 本地构建 | 状态 |
|---|---|---|---|---|
| macOS | arm64 | `macos-latest` | Apple Silicon Mac | ✅ 已有 |
| macOS | x86_64 | `macos-13` | Intel Mac | 🆕 Phase 3 |
| Linux | x86_64 | `ubuntu-latest` | x86_64 Linux | ✅ 已有 |
| Windows | x86_64 | `windows-latest` | Windows | ⚠️ Phase 1 加诊断 |

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Profiling 揭示的瓶颈与预期不符 | Phase 2 优化方向调整 | 数据驱动，不受预期约束 |
| 裁剪依赖导致运行时错误 | 功能异常 | 每个裁剪操作独立验证，失败即回滚 |
| `macos-13` runner 将来被 GitHub 废弃 | Intel 构建中断 | 关注 GitHub runner deprecation 通知，提前迁移 |
| Windows smoke test 无法复现现场失败 | 诊断困难 | 收集足够诊断信息，必要时在用户环境远程排查 |

- **Linux arm64 便携版**——当前无需求，后续可按相同模式扩展
