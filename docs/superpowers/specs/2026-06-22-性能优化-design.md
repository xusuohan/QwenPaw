# QwenPaw 系统性能优化设计

- 日期：2026-06-22
- 分支：`feature/usb-portable`
- 状态：已评审，待实施计划
- 范围：整体优化系统性能，覆盖三大核心场景——程序启动阶段 IO 卡顿、对话交互运行时响应延迟、架构底层读写资源竞争冲突；并专项处理启动期 Python import 的 4K 随机读写问题。

## 1. 目标与约束

### 1.1 目标

- **场景一（启动 IO）**：让 `_app.py` lifespan Phase 1 回到 <100ms 目标，缩短"首个 Agent 可用"时间；消除启动期 Python import 在 exFAT 上的 4K 随机读写放大。
- **场景二（运行时延迟）**：压低首 token 延迟（TTFT），消除请求热路径上的同步文件 IO 与事件循环阻塞。
- **场景三（资源竞争）**：消除并发下的配置/会话/日志数据丢失与损坏，修复潜在死锁。

### 1.2 已确认约束（来自澄清问答）

| 约束 | 决定 | 影响 |
|---|---|---|
| 部署目标 | **USB 便携版优先（exFAT）** | 减磁盘往返、原子写健壮性、文件锁语义进核心范围；普通安装版顺带受益 |
| 并发模型 | **单实例，仅进程内并发** | 资源竞争只需进程内锁 + 原子写；跨进程锁仅 `backup/safe_swap` 保留 |
| 行为变更 | **可接受小幅行为变更** | 鉴权短 TTL 缓存、遥测后台化、关键写加 fsync 均可用 |
| 请求路径深度 | **中等：仅复用模型/客户端** | 模型/httpx 客户端 per-agent_id 缓存；Agent 实例仍按现状重建 |
| 宿主磁盘 | **不碰宿主磁盘** | import 优化不用"拷本地影子"，仅用构建期 + 进程内手段 |

### 1.3 现状基线（已确认的瓶颈，详见附录 A）

- 启动：遥测在 Phase 1 同步 HTTP+子进程（最坏 5s）；skills 迁移每次冷启全文件 sha256 扫描；多处 import 期扫盘；构建用 mtime 校验 .pyc（exFAT 易触发重编译写）。
- 运行时：每请求重建 `QwenPawAgent` + 新建 `AsyncOpenAI`/httpx 连接池；`save_session_state` 同步写阻塞事件循环；`chats.json` 每请求 2 次全文件 IO；`AuthMiddleware` 每请求读 `auth.json` 多达 3 次。
- 竞争：`config.json`/`agent.json`/`session.json`/`auth.json` 等 8 类裸覆写无锁无原子；`ChannelManager.replace_channel` 持锁内 `await stop()` 自死锁风险；日志多进程交错写。
- 已有正面模板（本设计以它们为蓝本）：`backup/_utils/safe_swap.py`、`agents/skills_manager.py:519`、`token_usage/storage.py`。

## 2. 整体架构

建两个共享"基石"模块（置于 `src/qwenpaw/utils/`，与现有 `logging.py`/`system_info.py` 同级），再用它们系统化治理三大场景。

### 2.1 基石 1：`utils/atomic_io.py` — 安全 JSON 读写

把项目里三处已验证的好模式（`skills_manager._write_json_atomic`、`token_usage/storage.py`、`backup/safe_swap`）抽成统一工具：

- `write_json_atomic(path, data, *, lock=True, fsync=True)`：同目录写 `path + ".tmp.<pid>"` → `json.dump` →（可选）`fsync(tmp)` → `os.replace(tmp, path)`（exFAT 上 best-effort）→ 清理同前缀孤儿 `.tmp`。
- `locked_json_update(path, fn)`：进程内锁包住整个 **read-modify-write**；`fn` 收到旧数据返回新数据。用 `threading.RLock`（可重入）避免回调自死锁，文档约束回调内不得再触发同路径写。
- `read_json_safe(path)`：读 + `json_repair` 兜底（复用 `config/utils` 现有兜底）。
- `cleanup_orphan_tmps(dir)`：启动期清理上次崩溃遗留的 `.tmp.<pid>`。
- `write_bytes_atomic(path, data)`：字节版（用于 secret key）。
- **进程内锁**：模块级 `path → threading.RLock` 注册表（受一把 meta-lock保护）。单实例约束下不需要跨进程锁。
- **exFAT 适配**：`fsync` 文件；目录 fsync 仅 Linux/macOS 尽力而为，Windows 跳过；`chmod 0o600` 在 exFAT 无效——工具内不依赖它，安全注释说明。

### 2.2 基石 2：`utils/background_tasks.py` — 受管后台任务

轻量注册表，在运行中的 event loop 上派发"即发即弃"任务，lifespan 关闭时统一 cancel。区别于 `_background_startup`（Agent 加载）：承接**非关键的可延迟小 IO**（遥测、冗余迁移校验、import 预读、token 计数预热）。

### 2.3 集成图

## 3. 场景一：启动 IO 卡顿

### 3.1 遥测采集移出阻塞路径（最大单点收益）

- **问题**：`_app.py:247-261` 在 Phase 1 同步调 `collect_and_upload_telemetry`，内部（`telemetry.py:84/102/127`）同步 HTTP POST（httpx timeout 2s）+ `nvidia-smi`/`lspci`/`wmic` 子进程（各 3s 超时），最坏阻塞 5s。
- **改动**：保留"首次未采集才上报"判定（读 marker，几 ms），把"采集+上报"整段丢进 `BackgroundTaskRunner`（延迟 ~2s 触发，让路 HTTP 就绪）。marker 写入走 `atomic_io`（顺带修 telemetry marker 裸覆写）。
- **语义变化**：遥测从"首启阻塞上报"变为"首启后台上报"（已确认可接受）。

### 3.2 迁移函数幂等化（消除每次冷启重复扫盘）

- **问题**：`migrate_legacy_skills_to_skill_pool`（`migration.py:297`）每次冷启对每个 workspace × 每个 skill `rglob` + sha256；`migrate_legacy_workspace_to_default_agent`（`:56`）每次 8 个 item stat + md glob。
- **改动**：引入启动迁移戳 `.qwenpaw_data/.migration_stamp`（JSON：`{qwenpaw_version, manifest_version, ts}`）。Phase 1 三个迁移 + `ensure_*` 先读戳（1 次 stat），版本未变整体跳过扫描，后台异步校验一次；戳变化或缺失才完整迁移。戳写入用 `atomic_io`。

### 3.3 import 时的磁盘扫描延迟化

- **`constant.py:143 _discover_agent_languages`**：随包发布的静态内容，语言集合（en/local/qa/ru/zh）构建期已知 → 硬编码集合 + 一次性惰性校验，消除每次进程启动扫盘。
- **`_app.py:69 load_envs_into_environ`**：从模块顶层移到 lifespan Phase 1（`cleanup_startup_restore_artifacts` 之后），不再在 `import qwenpaw.app._app` 时于 restore 锁内执行。
- **`_app.py:597 _resolve_console_static_dir`**：调整候选路径探测顺序（包内 `console/` 命中率最高置首 + 命中即短路）。

### 3.4 restore 清理的 stat 精简（保持同步）

- **问题**：`cleanup_startup_restore_artifacts`（`safe_swap.py:222`）每个 profile workspace 做 resolve + 2~3 次 tmp/old stat，多 agent 线性增长；必须同步（restore 安全性）。
- **改动**：保持同步语义；(a) 缓存 profile→workspace_dir 的 resolve 结果（Phase 1 内复用）；(b) 每个 target 的 tmp/old/mount stat 合并为一次 `os.scandir`（exFAT 上 1 次列举 ≪ 3 次 stat）。

### 3.5 Workspace.start 冗余去重（压短"首个 Agent 可用"）

- **问题**：每个 agent 的 `Workspace.start`（`workspace.py:350`）都调 `ensure_skill_pool_initialized`，但 skill 池**共享** → N agent 重复初始化 N 次；`_migrate_legacy_weixin_data` 也每个 agent 重跑 stat。
- **改动**：`ensure_skill_pool_initialized` 提升为 `MultiAgentManager` 级一次性初始化；weixin 迁移 stat 结果本次启动内缓存。

### 3.6 py import 4K 随机读写优化（专项）

#### 3.6.1 哈希 .pyc（构建期，治"写"）

- **问题**：构建用 `compileall -q -j 0` 默认 **mtime 校验**。exFAT 上 mtime 在 conda-pack/解压/拷贝过程易漂移，Python 判定 .pyc 过期 → import 时重编译写 .pyc（U 盘随机写极慢）。
- **改动**：所有 `compileall` 加 `--invalidation-mode checked-hash`：
  - `scripts/pack/build_linux.sh:51`
  - `scripts/pack/build_macos.sh:58`
  - `scripts/pack/build_win.ps1:213`
  - `scripts/pack/build_win_portable.ps1:201`
- import 时按内容哈希校验而非 mtime → 消除 import 期重编译写。哈希校验比 mtime stat 略贵，但省下远为昂贵的随机写；哈希只算一次嵌入 .pyc 头。Python 3.7+ 标准特性，风险低。

#### 3.6.2 import 顺序预读预热（运行期，治"读"）

- **新增** `src/qwenpaw/utils/import_prefetch.py`：进程启动最早期（`qwenpaw app`/`desktop` 入口、重 import 链开始前）派后台线程，按 import 顺序顺序预读 site-packages + qwenpaw 的 `.pyc`/`.pyd`，随机读转顺序读、提前填 OS 页缓存。
- **顺序来源**：`python -X importtime` 采集冷启 import 顺序生成清单 `.qwenpaw_data/.import_order`。首启无清单时退化为目录序顺序全扫（仍是随机→顺序收益）。
- **边界**：单预读线程 + OS readahead，避免与 import 抢 USB 单队列；按 `QWENPAW_PERF_PREFETCH_CAP_MB`（默认 256MB）截断，优先 `.pyc` 跳过已热。
- **生命周期**：Phase 1 启动、best-effort、绝不阻塞；import 链追上或关闭时停。开关 `QWENPAW_PERF_IMPORT_PREFETCH`（默认开）。

#### 3.6.3 度量与基线

- 现有 `startup_profile/tracer.py` 只追 `qwenpaw.*`，测不到依赖 import 耗时（盲区）。本节用它 + `python -X importtime` 采集 USB 冷启基线，改造前后对比：(a) import 期 .pyc 写次数（哈希 .pyc 后应≈0）、(b) import 总墙钟时间、(c) 冷启到 HTTP ready。import 顺序清单既是预读输入、也是度量产物。

## 4. 场景二：对话运行时响应延迟

约束：仅复用模型/客户端，Agent 实例仍按现状重建。

### 4.1 模型/httpx 客户端 per-agent_id 缓存（最大 TTFT 收益）

- **问题**：`runner.py:570` 每请求重建 `QwenPawAgent` → `model_factory.py:1009 create_model_and_formatter` → `openai_provider.py:150` 每次新建 `OpenAIChatModelCompat` → 新建 `AsyncOpenAI`/httpx 客户端（冷连接池 + TLS 握手，可达 100ms+/请求）。
- **改动**：`ProviderManager`（单例）加 per-agent_id 模型客户端缓存。命中返回既有客户端，复用其 httpx 连接池，消除每请求 TLS 重连。Agent 实例照常重建。
- **缓存键**：`agent_id`。
- **失效**：任何对该 agent 的配置保存（`save_agent_config`，已走 `atomic_io`）→ 驱逐；provider 变更同理。复用已有 `AgentConfigWatcher` 回调；`save_agent_config` 在 atomic_io 写完后**主动调一次驱逐**作为双保险（api_key 轮换属配置保存，自动覆盖）。

### 4.2 save_session_state 异步化

- **问题**：`session.py:271` 用同步 `open()` + `json.dumps`（请求 finally），而 `load_session_state:315` 已用 aiofiles——写路径阻塞事件循环，长对话可达数十 ms。
- **改动**：写路径改 `await asyncio.to_thread(atomic_io.write_json_atomic, path, data)`。基石 1 的 `RLock` 天然适配 `to_thread`；aiofiles 写、`os.replace` 原子提交。顺带把 session 写纳入原子保护（修场景三 C2）。

### 4.3 chats.json 内存缓存 + 后台 flush

- **问题**：`runner/manager.py:107 get_or_create_chat` → `repo.load()` 全文件读，`runner.py:796 touch_chat` → `repo.save()` 全文件重写，每请求 2 次同步全文件 IO，无缓存。
- **改动**：照搬 `token_usage` 模式——`JsonChatRepository` 加 per-agent 内存缓存：读命中缓存；写更新缓存 + 标脏，后台任务按 `flush_interval` 批量落盘 + shutdown 强制 flush；增删 chat 同步更新缓存。落盘走 `atomic_io`（修场景三 M4）。

### 4.4 auth.json TTL 缓存 + 请求内去重

- **问题**：`auth.py` AuthMiddleware 每请求读 `auth.json` 多达 3 次（`verify_token`→`_load_auth_data`、`_is_token_revoked`→再读、`_should_skip_auth`→`has_registered_users`→第三次）+ 每次解密，无缓存。
- **改动**：内存缓存 `jwt_secret` + 已撤销 token 列表，TTL ~3s（撤销延迟 ≤TTL，已确认可接受）；请求内去重，单请求只 `_load_auth_data` 一次；撤销 token 的 API 端点立即清缓存（正常撤销路径无延迟）。

### 4.5（次要）tool result 写异步 + token 计数增量缓存

- **问题**：`light_context_manager.py:175-180 post_acting` 可能同步 `write_text` 落盘裁剪后 tool result；`pre_reasoning:710` 每轮对全历史重算 token（轻量字节除法，长历史 + 多轮仍累计）。
- **改动**：tool result 落盘走 `asyncio.to_thread` + atomic_io；token 计数加增量缓存（按消息列表长度 + 末尾内容指纹，仅对增量计数，压缩/摘要失效）。**优先级低于 4.1–4.4**，作收尾。

## 5. 场景三：读写资源竞争

单实例约束下只需进程内锁 + 原子写（跨进程锁仅 `backup/safe_swap` 保留）。

### 5.1 系统性应用 atomic_io（基石 1 落地）

| 站点 | 现状 | 改为 |
|---|---|---|
| `config.py:790 save_config` / `:1871 save_agent_config`（C1） | 裸 `open("w")`，锁仅缓存失效 | `locked_json_update`（RMW 全程持锁）|
| `session.py:288 save_session_state`（C2） | 裸 `open("w")`，注释承认竞态 | 已由 4.2 覆盖 |
| `auth.py` 写 `auth.json` | 裸覆写 | `write_json_atomic` |
| `dingtalk/channel.py:458`（H1） | 裸 `open("w")`，内存锁不护磁盘 | `write_json_atomic` |
| `dingtalk/ai_card.py:54-78`（H2） | 已 tmp+replace，无锁 | `write_json_atomic`（补锁）|
| `local_models/manager.py:82`（H2） | 裸 `open("w")` + chmod | `write_json_atomic` |
| `crons/repo/json_repo.py` / `runner/repo/json_repo.py`（M4） | 已 tmp+move，无锁 | `write_json_atomic`（补进程内锁；chats 侧由 4.3 缓存承接）|
| `telemetry.py:281`（H3） | 裸 `write_text` | 已由 3.1 覆盖 |
| `security/secret_store.py:139`（L5） | `write_text` + chmod | 见 5.4 |

### 5.2 ChannelManager 死锁修复（M1）

- **问题**：`channels/manager.py:741 replace_channel` 在 `async with self._lock:` 内 `await old_channel.stop()`；若 `stop()` 回调 `get_channel`/`enqueue`（需同把锁），asyncio.Lock 不可重入 → 自死锁，整个 channel manager 挂起。
- **改动**：照搬同文件 `restart_channel:597` 已正确模式——**持锁做 dict swap，锁外 stop 旧实例**：
  ```python
  async def replace_channel(...):
      async with self._lock:
          old = self._channels[key]
          self._channels[key] = new      # swap 持锁
      await old.stop()                   # 锁外 stop
  ```
- 配套：审计 `ch.stop()` 回调路径；即便不反查 manager，也按防御式改写（与 `restart_channel` 对齐）。

### 5.3 日志多进程/多线程竞态（C3）

- **问题**：`utils/logging.py:88 _SafeRotatingFileHandler` 只对 Windows 轮转 `PermissionError` 容错，不防多进程交错写 + 轮转丢日志。单实例下仍有两进程：desktop 启动器 + backend 子进程（Windows 上 backend stdout 经线程流转）。
- **改动**（两层）：
  - **进程内**：`QueueHandler` + `QueueListener`——logger 投递到队列，单一 listener 线程 owns 文件 handler，写日志不阻塞请求线程、无交错。
  - **跨进程**：desktop 启动器与 backend 各写**独立日志文件**（`qwenpaw-backend.log` / `qwenpaw-desktop.log`），从根上消除两进程争抢同一文件。backend stdout 流（Windows `_stream_reader`）保留用于实时排障。

### 5.4 secret_store master key 首启原子化（L5，边角）

- **问题**：`security/secret_store.py:139 _write_key_file` 用 `write_text` + chmod，首启多协程可能各自生成不同 key 互相覆盖 → 已加密 secret 解不开。
- **改动**：`O_CREAT|O_EXCL` 原子创建（赢家写、败者直接读赢家），写盘走 `write_bytes_atomic`。chmod 在 exFAT 无效——注释说明，不依赖。

## 6. 跨场景：数据流、错误处理、测试、度量、回滚

### 6.1 数据流

**启动流**（改造后）：
```
import qwenpaw.app._app        # 无扫盘（3.3：语言列表硬编码、envs/console 延迟）
                              # + import 预读线程启动（3.6.2）
 → lifespan Phase 1（<100ms 目标）
    ├ cleanup_startup_restore_artifacts（3.4 精简 stat，保持同步）
    ├ load_envs_into_environ（从 import 移到这里）
    ├ 4 个迁移函数（3.2：读戳命中→跳过；未命中→完整迁移+后台校验）
    ├ 遥测判定 → 采集上报丢进 BackgroundTaskRunner（3.1）
    └ managers 构造（无 IO）
 → "Server ready"（HTTP 可接受请求）
 → Phase 2 后台：agents 预热（3.5 skill 池去重）+ bg tasks（遥测、迁移校验、预读尾段）
```

**请求流**（改造后）：
```
HTTP → AuthMiddleware（4.4：TTL 缓存命中 → 0 次读盘）
 → runner → create_model_and_formatter（4.1：client 缓存命中 → 复用 httpx 连接池）
 → ReAct 循环（4.5：增量 token 计数）
 → finally：save_session_state（4.2：to_thread + atomic_io，不阻塞 loop）
 → touch_chat（4.3：更新内存缓存，标脏，后台 flush）
```

### 6.2 错误处理（关键失效模式）

| 失效 | 处理 |
|---|---|
| `atomic_io` 写失败（盘满 / exFAT rename 失败） | 清理 tmp、原文件不动、向上抛（调用方决策）；`json_repair` 兜底读 |
| 后台任务失败（遥测/迁移校验/预读） | 仅记日志，绝不阻塞启动或请求 |
| 模型客户端缓存过期 | 双重驱逐（watcher 回调 + `save_agent_config` 主动驱逐）兜底 |
| chats flush 失败 | 重试 + 建/删 chat 立即 flush |
| 迁移戳损坏/缺版本 | 视为"需完整迁移"（安全默认），重跑 |
| import 预读与 import 抢 USB 队列 | 单线程 + OS readahead + 顺序化 + 上限；实测反噬则降为子集 |
| import 顺序清单过期 | 版本号变化重新采集；缺失/过期退化为目录序全扫，不报错 |
| `locked_json_update` 回调内同路径写 | `RLock` 可重入 + 文档约束回调禁同路径写 |

### 6.3 测试

- **atomic_io**：多线程并发写（assert 无损坏/无丢失）、模拟 `os.replace` 失败（assert 原文件完整 + tmp 清理）、孤儿 `.tmp` 清理、`json_repair` 读兜底、`RLock` 可重入。
- **模型客户端缓存**：命中/未命中、`save_agent_config` 后驱逐、api_key 变更触发失效。
- **session/chats 异步化**：请求路径零同步文件写（事件循环不被阻塞的时序断言）、shutdown 强制 flush、flush 失败重试。
- **auth TTL 缓存**：过期重载、撤销端点立即清缓存、单请求内只读一次盘。
- **迁移戳**：版本匹配跳过、版本变更重跑、损坏 → 安全重跑。
- **ChannelManager**：`replace_channel` 在 `stop()` 反查 manager 时不死锁（回归测试）。
- **日志**：双进程写各自文件无交错、QueueListener 不丢日志。
- **import 优化**：构建产物 `.pyc` 头为 hash 模式（断言）；冷启 import 期 `.pyc` 写次数≈0（strace/fsutil 计数）；预读前后 import 墙钟对比。
- **回归**：现有 `tests/` 全绿。

### 6.4 度量

复用 `_app.py` 已有 `startup_start_time` 计时 + 少量探针，改造前后各跑一次基线（USB/exFAT 真机）：

| 指标 | 目标 |
|---|---|
| Phase 1 时长（HTTP ready） | < 100ms（遥测移除前最坏 ~5s）|
| 首个 Agent 可用（Phase 2 完成） | 显著下降（skill 池去重 + 无重复迁移扫描）|
| import 总墙钟时间 | 哈希 .pyc + 预读后下降（`-X importtime` 采集）|
| import 期 .pyc 写次数 | ≈ 0（哈希 .pyc）|
| TTFT（请求到首 token） | 消除每请求 TLS 重连（估 -50ms+）|
| 请求热路径同步文件写 | 0 次（session/chats/auth 全异步或缓存）|
